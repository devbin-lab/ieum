# 상태와 담당자 전달 분리 계획

> 2026-10-08 이후 정책은 [일정과 작업 잠금](task-lock-and-schedule-plan.md)을 따릅니다. 아래 내용은 이전 구현 기록입니다. 반려와 자동화는 제거되었으며 잠근 작업은 잠금 담당자만 수정합니다.

## 요청과 분석

작업 상태는 확인중·진행중·완료로 유지한다. 진행중인 작업을 다음 담당자에게 넘길 때 상태를 초기화하거나 다른 참여자의 편집을 차단하지 않는다. 현재 담당자는 내 할 일과 알림을 위한 배정 정보다.

현재 기본 전달은 `doing → todo`이며 `canEditWorkflowTask`와 `availableWorkflowRoutes`가 현재 수신자와 상태 편집 정책을 검사한다. 모든 전달 버튼이 시트 경로에 의존한다. `assigneeId`는 최초 작업 담당자이므로 여러 번 전달한 뒤의 반려 대상을 표현할 수 없다. SQLite, GitHub 제출, 통합은 같은 변경 검증기를 사용하므로 화면과 저장소만 고쳐서는 전달이 실제로 통합되지 않는다.

## 실행 계획

1. 현재 담당자와 편집 가능 여부를 분리한다. 미완료·미보관 작업은 활성 프로젝트 참여자가 편집할 수 있도록 공통 정책을 변경한다.
2. 설정된 연결 없이도 실행할 수 있는 담당자 전달과 상태 변경을 제공한다. 전달은 기존 상태를 유지하고, 처리 시작·최종 완료는 별도 동작으로 표시한다.
3. 직전 실제 전달자의 ID를 작업에 저장한다. 반려는 코멘트를 필수로 받아 해당 전달자에게 다시 배정하며 상태를 유지한다. 비활성 대상은 선택할 수 없다.
4. 전달 대상·목적·버전·코멘트를 최종 확인한 뒤 원자적으로 저장한다. 내 할 일, 이력, 알림, 제출 증명과 충돌 병합에 같은 배정 정보를 사용한다.
5. 기본 시트의 전달·반려를 진행중 자기 연결로 변경한다. 시트는 선택 가능한 전달 설정으로 사용하며, 시트 조건이 직접 전달을 막지 않도록 한다. 설정 화면의 담당자 기반 편집 잠금 설명·선택을 제거한다.
6. 기존 프로젝트·작업·미전송 변경을 일괄 재작성하지 않고 새 공통 동작을 제공한다. 기존 검토·재작업 상태는 진행중 열에서 표시한다.
7. 모델·저장소·GitHub 모의 통합·최종 확인 UI에 필요한 회귀를 추가하고 정적 분석, Windows Release 빌드·시작 확인을 수행한다. 실제 팀 조작 검증은 사용자에게 맡긴다.

## 코드 경계

- 모델·공통 엔진·저장소: 담당자와 수정 정책, 직접 전달·반려·상태 변경, 직전 전달자, 버전과 수신자 검증, 원자적 저장 및 병합.
- 확인창·작업 편집창: 상태 유지 안내, 받는 담당자 선택, 처리 목적, 반려 코멘트, 최신 정보 재확인.
- 프로젝트 화면·설정: 시트와 독립적인 공통 작업 버튼, 고정 3열, 현재 담당자와 내 할 일, 선택 가능한 전달 설정의 설명.
- GitHub: 공통 변경 검증, 작성자 확인, 최신 기준 버전, 제출 증명, 내용 수정과 전달 병합, 서로 다른 수신자의 충돌 보존.

## 검증 기준

기획 → QA → PD 전달에서 상태가 계속 진행중이어야 한다. 전달 후 기획자도 내용을 수정할 수 있어야 한다. PD의 반려는 최초 기획자가 아니라 직전 전달자인 QA에게 돌아가야 한다. 직접 전달은 시트가 없거나 특정 파트의 경로가 없어도 가능해야 한다. 확인 취소·비활성 수신자·오래된 버전은 작업을 변경하지 않아야 한다. 같은 상태의 전달과 후속 편집이 GitHub 제출·통합을 통과하고, 서로 다른 담당자 전달은 섞이지 않아야 한다.

- 모델·공통 엔진·저장소·프로젝트 화면·설정·GitHub 검증기 연결 완료.

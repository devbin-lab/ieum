# 이음 1.0.0 · Flutter 데스크톱 앱

이음은 GitHub 저장소를 팀 데이터의 기준으로 사용하는 작업·일정 관리 앱입니다. 각 사용자의 PC에는 SQLite로 작업을 저장하고, 변경 사항을 GitHub에 반영해 팀원과 공유합니다. 별도 업무 서버를 운영할 필요가 없습니다.

이 문서는 현재 Flutter 앱의 기능과 개발 방법을 설명합니다. 배포 파일은 [GitHub Releases](https://github.com/devbin-lab/ieum/releases)에서 확인할 수 있습니다.

## 설치와 첫 프로젝트

Windows x64 배포 파일을 사용하는 경우 개발 도구를 설치할 필요가 없습니다.

1. 설치형 `Ieum-Setup-x64.exe`를 실행하고 설치 위치와 바로가기 옵션을 선택합니다. 기본 설치 위치는 `%LOCALAPPDATA%\Programs\Ieum`이며 관리자 권한이 필요하지 않습니다. 포터블 배포는 `Ieum-Windows-x64.exe`를 실행합니다. ZIP 배포 파일을 사용한다면 전체를 압축 해제하고 `ieum_flutter.exe`를 실행합니다. 실행 파일만 ZIP 밖으로 옮기면 안 됩니다.
2. 첫 실행에서 언어·화면 모드·포인트 컬러를 선택하거나 초기 설정을 건너뜁니다. **GitHub로 로그인**을 선택하고 브라우저에서 인증 코드를 승인합니다. 로그인 유지를 선택하면 인증 정보는 Windows 자격 증명 보관소에 저장됩니다.
3. 저장소 관리자는 프로젝트 이름, GitHub 저장소와 닉네임을 입력해 **프로젝트 생성**을 진행합니다. 한 저장소에 하나의 이음 프로젝트를 만들며 빈 저장소도 초기화할 수 있습니다.
4. 팀원을 GitHub 저장소 협업자로 초대합니다. 초대를 수락한 팀원은 이음에서 같은 저장소에 **프로젝트 참여**를 요청하고, 프로젝트 소유자가 승인합니다.
5. **프로젝트 설정 → 파트**에서 필요한 파트를 만들고 **참여자 관리**에서 배정합니다. 소유자도 파트를 배정받을 수 있습니다.

새 프로젝트의 작업, 파트와 등록된 바로가기는 비어 있습니다. 프로젝트 소유자의 관리 권한만 기본으로 유지하며 예시 작업이나 기본 직군을 자동 생성하지 않습니다.

초기 설정을 완료하거나 건너뛰면 다음 실행에 반복하지 않습니다. 기존 설정·최근 프로젝트가 있는 사용자는 기존 진입 흐름을 유지합니다. 화면 모드와 언어는 개인 설정에서 다시 변경할 수 있습니다. Windows 설정의 **앱 → 설치된 앱**에서 이음을 제거하면 설치 파일과 바로가기만 정리하며 프로젝트·개인 설정·자격 증명은 보존합니다.

저장 위치는 자동으로 준비됩니다. 생성·참여 화면의 **저장 위치 변경**으로 다른 폴더를 선택할 수 있으며, 기존 프로젝트와 다른 프로젝트는 프로젝트 선택기에서 열고 전환합니다. 로그아웃해도 로컬 프로젝트 데이터는 지워지지 않습니다.

## 화면 구성

| 화면 | 주요 기능 |
| --- | --- |
| 작업 | 목록·칸반 전환, 검색과 필터, 정렬, 작업 등록·상세·전달, 보관함 |
| 일정 | 작업 기간을 달력·날짜별 목록·타임라인으로 확인 |
| 타임라인 | 프로젝트 변경 기록과 관련 작업 확인 |
| 연결 | GitHub 연결, 동기화 상태, 전송 대기·충돌·복구 기록 확인 |
| 바로가기 | 팀 링크 등록·열기, 서비스 카탈로그, 검색·즐겨찾기 |
| 알림 | 본인 담당 작업 알림과 상세 확인, 관련 작업으로 이동 |
| 프로젝트 설정 | 프로젝트 정보, 자료 한도, 참여자·파트 관리, Discord 알림 |
| 개인 설정 | 이름, 라이트·다크 모드, 포인트 컬러, 한국어·영어, 앱 정보 |

프로젝트 사이드바의 열림 상태는 화면을 이동해도 유지됩니다. 알림에서 작업을 열면 마지막으로 사용한 작업 목록·칸반 또는 일정 화면에서 해당 작업을 확인합니다. 프로젝트의 전체 변경 기록은 **타임라인**에서 확인합니다.

디자인과 언어 설정은 개인 PC에 저장됩니다. 화면 모드는 라이트·다크·기기의 화면 설정을 따르는 시스템 중 선택합니다. 화면의 한국어·영어 표시는 바뀌지만 사용자가 입력한 작업 내용과 프로젝트 이름은 번역하지 않습니다. 포인트 컬러에는 사용자 지정 색상과 라이트 모드에서 검은색, 다크 모드에서 흰색을 사용하는 흑백 옵션이 있습니다. 일정의 오늘 날짜는 포인트 컬러와 별도로 빨간색으로 표시합니다.

## 작업 상태와 전달

칸반은 다음 여섯 상태를 사용합니다.

| 상태 | 용도 |
| --- | --- |
| 확인중 | 전달받았거나 아직 시작하지 않은 작업 |
| 진행중 | 작성·제작·수정 중인 작업 |
| 검토중 | 결과를 검토하는 작업 |
| 완료 | 작업이 끝난 상태 |
| 보류 | 사유를 남기고 잠시 멈춘 작업 |
| 드랍 | 진행하지 않기로 한 작업 |

상태와 담당자는 별도로 관리합니다. 확인중은 알림의 읽음 여부와 다릅니다. 진행중·검토중에서 **전달**을 선택하면 받을 파트 또는 담당자, 작성·검토·수정 목적과 코멘트를 지정하고 최종 확인합니다. 전달된 작업은 확인중으로 이동하며, 담당자가 시작하면 목적에 따라 진행중 또는 검토중으로 이동합니다.

검토 의견은 코멘트로 남기고 필요하면 수정 목적으로 다시 전달합니다. 별도 반려 기능과 사용자 정의 자동화 시트는 제공하지 않습니다. 보류·드랍에는 사유가 필요합니다. 보류는 이전 상태로 재개하고 드랍은 확인중으로 복귀합니다.

잠금 없는 확인중·진행중·검토중 작업의 내용은 모든 활성 참여자가 수정할 수 있습니다. 완료·보류·드랍 상태에서는 내용을 직접 수정하지 않습니다. 담당자와 파트는 내 할 일 및 알림 대상을 정하는 정보입니다. 작업 수정에 예전의 기능별 권한을 추가로 부여할 필요는 없으며, 별도로 설정하는 관리 권한은 **참여자 관리**와 **파트 관리**입니다.

### 작업 잠금

새 작업에서 **잠금 없음**, **작성자만 수정**, **지정 작업자만 수정**을 선택합니다. 등록한 작업은 상세 화면에서 본인 작업으로 잠글 수도 있습니다.

잠금 담당자만 내용·상태·전달·삭제·보관을 변경할 수 있습니다. 다른 활성 참여자는 열람하고 코멘트를 남길 수 있으며, 프로젝트 관리자도 다른 사람의 잠금을 임의로 해제할 수 없습니다.

**잠근 채 전달**하려면 받을 담당자 한 명을 지정해야 합니다. 전달과 잠금 담당자 변경은 함께 저장되며 이전 담당자는 수정할 수 없게 됩니다. 잠금을 풀고 파트 전체에 전달하면 해당 파트 구성원에게 배정되지만 내용 수정은 모든 활성 참여자에게 허용됩니다. 확인창을 연 뒤 작업이나 참여자 정보가 바뀌면 다시 확인해야 합니다.

### 정리와 기록

- 작업을 **상단에 고정**하면 일반 작업보다 앞에 표시합니다. 고정 작업끼리는 높음·보통·낮음 우선순위를 따릅니다.
- 보관한 작업은 목록과 일정에서 숨기고 보관함에서 복원합니다.
- 작업 상세의 **삭제**는 확인 후 처리되며 앱에서 복원할 수 없습니다. 삭제된 작업이 동기화 후 다시 나타나지 않도록 삭제 표식을 유지합니다.
- 상세에서 작성자·작성일, 현재 담당자와 전달·상태 변경 기록을 확인합니다. 작성 기록이 없는 과거 작업은 추측해서 채우지 않습니다.
- 코멘트는 작성자와 시각을 함께 저장하며 작업당 100개, 각 2,000자까지 등록합니다.

## 일정과 작업 자료

일정은 **작업 지정일~마감일을 양 끝 날짜까지 포함**합니다. 같은 작업은 날짜 칸을 가로지르는 연속 막대로 표시하고, 주가 바뀌면 다음 줄에서 이어집니다. 일정 색은 작업 상태와 일치합니다. 마감일이 없으면 지정일에 표시하고 마감 미정 목록에 남습니다. 보관·삭제·드랍 작업은 일정에서 제외합니다.

작업 상세의 **자료**에서 파일과 HTTPS 링크를 합쳐 최대 30개까지 첨부합니다. 파일당 기본 한도는 **50MB**이며 프로젝트 소유자가 **프로젝트 설정 → 일반 → 자료**에서 **1~50MB**로 조절합니다. 변경한 한도는 새 파일에 적용하고 기존 자료는 유지합니다. 자료 추가·제거에도 작업 잠금이 적용됩니다.

작업 설명은 Markdown으로 표시합니다. `.md`·`.markdown` 첨부 파일은 앱 안에서 펼쳐 읽으며 미리보기 한도는 256KB입니다. 다른 형식과 더 큰 Markdown 파일은 다운로드해 확인합니다. 문서의 외부 이미지는 자동으로 내려받지 않습니다.

파일 내용은 작업 JSON과 분리하여 저장소의 `ieum/attachments` 브랜치에 저장합니다. 같은 파일은 중복 업로드하지 않으며 업로드가 완료된 뒤 작업 변경을 제출합니다. 자료를 제거하면 작업과의 연결만 해제합니다. GitHub에 저장한 파일과 커밋 이력은 자동 삭제하지 않습니다.

## 팀 바로가기

**등록된 바로가기**에는 팀 폴더·문서·보드·채팅방 등의 HTTPS 주소를 추가합니다. **도구 추가**는 Google Drive, Notion, Jira, Discord, 카카오톡, GitHub, Figma, Slack 카탈로그를 제공합니다. GitHub 저장소 주소를 기본 링크로 자동 등록하지 않습니다.

주소에 맞는 서비스와 사이트 아이콘을 인식하며 아이콘을 가져오지 못하면 서비스 SVG 또는 기본 링크 아이콘을 표시합니다. 카드에서 링크를 열고, 더보기에서 수정·복사·삭제합니다. 링크 목록은 팀과 공유하며 개인 즐겨찾기는 이 기기에 저장됩니다.

바로가기는 브라우저에서 주소를 여는 기능입니다. 해당 서비스의 계정 인증, MCP·에이전트 연결 또는 API 데이터 연동을 수행하지 않습니다. Discord 채널 알림 연결은 별도의 프로젝트 설정입니다.

## Discord 채널 알림 · Windows

Windows 앱의 **프로젝트 설정 → 알림**에서 Incoming Webhook으로 채널 알림을 연결합니다. 별도 서버·공유 봇·봇 토큰·GitHub Actions를 운영하지 않으며 개인 DM은 지원하지 않습니다.

1. 프로젝트 소유자가 Discord 채널의 웹훅 URL을 등록합니다. 앱은 조회 요청으로 서버·채널을 확인하며 등록 과정에 메시지를 보내지 않습니다.
2. 채널마다 **작업 배정·작업 전달·상태 변경·작업 완료**와 받을 파트를 선택합니다. 여러 채널을 연결할 수 있습니다.
3. 참여자는 같은 화면의 **내 Discord 계정**에 본인 숫자 사용자 ID를 등록합니다. 개인 담당자는 해당 ID로, 파트 전체는 활성 구성원의 등록 ID로 멘션합니다.
4. 최초 채널을 등록한 소유자 PC는 신뢰 기기가 됩니다. 다른 PC에서 전송하려면 소유자가 해당 참여자에게 개인 연결 코드를 전달하고, 참여자가 입력한 뒤 소유자가 기기 확인 코드를 대조해 승인합니다. 연결 코드는 15분간 유효합니다.

사용자 ID는 현재 프로젝트의 본인 정보에 저장됩니다. Discord 로그인이나 ID 소유권·서버 가입 확인을 수행하지 않으며 다른 프로젝트로 자동 전파하지 않습니다. 멘션을 받는 데에는 PC 승인이 필요 없습니다.

웹훅 URL과 개인키는 Windows 자격 증명 보관소에 저장합니다. 승인된 기기에 배포하는 연결 정보는 암호화하며 저장된 채널 카드에 URL을 표시하지 않습니다. 웹훅 주소와 연결 코드를 공개 저장소나 공개 채널에 게시하지 마세요.

알림은 **변경을 저장한 기기에서 자신의 변경이 GitHub 통합 브랜치에 반영된 뒤** 보냅니다. 다른 PC가 받은 변경을 다시 발신하지 않습니다. 원본 기기에서 앱을 닫으면 전송도 멈추며 같은 프로젝트를 다시 열면 대기 전송을 이어갑니다. 기기 승인 전에 저장한 변경은 소급 전송하지 않습니다.

파트별 채널 설정이 일치하면 모든 파트 설정보다 우선하며 같은 실제 채널에는 중복 게시하지 않습니다. 전송 기록에서 대기·실패·수신 미확정 상태를 확인하고 취소 또는 재전송할 수 있습니다. 수신 여부가 불명확한 경우 자동 재전송하지 않으며 수동 재전송에는 중복 가능성을 안내합니다.

기기를 해제하려면 일시 중지한 채널까지 포함해 Discord의 기존 웹훅을 삭제하고 새 URL을 등록해야 이미 전달한 토큰을 차단할 수 있습니다. 이음에서 채널 연결을 해제하는 것만으로 Discord 웹훅·채널·메시지를 삭제하지는 않습니다.

현재 Discord 자격 증명 보관과 기기 전송 잠금의 네이티브 구현 범위는 **Windows 1.0.0**입니다. Linux에서 같은 연결 기능을 지원한다고 보장하지 않습니다. 자세한 운영·보존 정책은 [Discord 채널 알림 설계](../docs/discord-webhook-design.md)를 참고하세요.

## 동기화와 로컬 데이터

작업 저장과 전송 대기열은 같은 SQLite 트랜잭션으로 기록합니다. 앱이 실행 중이면 작업별 브랜치·PR로 변경을 제출하고 참여자·버전·잠금·입력 규칙을 검증한 뒤 통합합니다. 다른 참여자는 통합된 데이터를 개인 DB로 가져옵니다.

로컬 저장과 팀 반영은 별도 상태입니다. 오프라인 변경은 보존되며 연결 화면에서 대기·오류·충돌을 확인합니다. 충돌한 내용은 임의로 덮어쓰지 않고 복구 가능한 기록을 남깁니다. 복구 경고의 **확인**은 이미 확인한 경고를 숨기며 나중에 생긴 새 복구 건은 다시 안내합니다.

GitHub에는 프로젝트 설정·작업 JSON·첨부 파일을 저장하고 개인 SQLite 파일은 업로드하지 않습니다. GitHub 저장소 쓰기 권한을 가진 사용자의 직접 수정까지 이음이 차단하지는 않습니다. 이음의 참여 중지와 GitHub 협업자 권한은 별도로 관리합니다.

| 로컬 항목 | 위치·용도 |
| --- | --- |
| 프로젝트 목록 | Windows 기본값 `%APPDATA%\Ieum-Flutter-Prototype\project-preferences.json` |
| 신규 프로젝트 DB | 위 설정 디렉터리의 `projects` 폴더. 저장 위치 변경 가능 |
| 프로젝트 DB 파일 | `ieum-<프로젝트 ID>-gh-<계정 ID>.sqlite` |
| 전송 대기 첨부 | DB 옆 `<DB 파일명>.resources/pending` |
| 다운로드 캐시 | 같은 자료 폴더의 `cache`. 용량을 제한하며 재다운로드 가능 |

프로젝트 DB를 옮길 때는 **전송 대기 첨부 폴더도 함께** 보존하세요. `IEUM_FLUTTER_DATA_DIR`로 설정 디렉터리를 지정할 수 있습니다. 인증 토큰·웹훅 비밀은 일반 설정 파일이나 배포 파일에 포함하지 않습니다.

Windows EXE 런처는 GitHub의 정식 Releases에서 업데이트를 확인합니다. 업데이트 파일의 크기·SHA-256을 검증하며 시작 실패 시 사용할 수 있는 이전 버전으로 복구합니다. 개발 실행에서는 `IEUM_DISABLE_UPDATES=1`로 자동 업데이트를 끌 수 있습니다.

## 개발과 패키징

현재 SDK 기준은 **Flutter 3.47.5 / Dart 3.13.4**이며 `pubspec.yaml`과 `lib/app_release.dart`의 앱 버전은 **1.0.0**입니다. Windows 빌드에는 Flutter SDK, MSVC C++ 빌드 도구와 CMake가 필요합니다.

`flutter_app` 디렉터리에서 실행합니다.

```powershell
flutter pub get
flutter analyze
flutter test test/task_resources_test.dart
.\build-windows.ps1
.\package-windows.ps1
```

변경한 영역에 맞는 단위·위젯 테스트를 선택합니다. 테스트는 임시·메모리 DB와 가짜 API를 사용하며 실제 프로젝트에 예시 작업을 등록할 필요가 없습니다.

[build-windows.ps1](build-windows.ps1)은 Windows Release를 빌드합니다. [package-windows.ps1](package-windows.ps1)은 기본 경로 `build/windows/x64/runner/Release`에서 버전과 필수 런타임·폰트·아이콘을 검사하고 배포 파일을 만듭니다. 다른 빌드 경로를 패키징하려면 `-ReleaseDirectory`를 지정하세요.

산출물은 저장소 루트의 `dist/windows/<빌드 시각>/`에 설치 EXE·포터블 EXE·ZIP·사용안내·`SHA256SUMS.txt`로 생성됩니다. 설치 패키지에는 Inno Setup 컴파일러가 필요하며 지정하지 않으면 고정 버전의 공식 빌드 도구를 검증해 저장소의 무시된 `.local/installer-tools/`에 준비합니다. 미리 준비한 컴파일러는 `-InnoCompiler <ISCC.exe 경로>`로 지정할 수 있습니다. 패키징 스크립트는 GitHub Release를 게시하거나 소스를 푸시하지 않습니다. 소스의 버전 확정과 배포 파일 게시 여부는 별개입니다.

Linux 소스와 [실행 안내](linux/README-Linux.md), [package-linux.sh](package-linux.sh)는 포함되어 있습니다. Linux 빌드에는 해당 환경의 Flutter·GTK 개발 도구가 필요하며 전체 번들을 압축 배포하고 수동 업데이트합니다. Windows 전용 기능은 플랫폼별로 별도 구현·검증해야 합니다.

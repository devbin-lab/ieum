# 이음 · GitHub 워크스페이스 1.0.0

이음은 GitHub 저장소를 팀 데이터의 기준으로 사용하고, 개인 SQLite에 작업을 저장하는 데스크톱 워크플로 앱입니다. 하나의 프로젝트 안에서 작업 목록·칸반, 일정, 담당자 전달·작업 잠금과 동기화 상태를 관리합니다.

Jira의 상태·전환·조건·입력 검증·전환 후 처리 구분을 참고해 설계했습니다. 이음의 운영 범위와 GitHub의 동기화 제약은 아래에 명시합니다. 실제 팀 환경의 수용 검증은 사용자가 수행합니다. 코드 검사와 배포 파일 검증은 별도로 진행합니다.

## 작업 공간

| 화면 | 역할 |
| --- | --- |
| 작업 | 목록·칸반 전환, 검색·파트·상태·마감 필터, 정렬, 작업 상세·전달·보관함 |
| 일정 | 같은 작업의 지정일·마감일을 달력과 타임라인에서 확인하고 상세로 이동 |
| 타임라인 | 프로젝트 전체 변경 기록과 관련 작업 확인 |
| 연결 | GitHub 저장소, 동기화 상태와 대기·보류 내용을 확인하고 연결 관리 |
| 바로가기 | 등록한 팀 링크 열기, 추천 도구 카탈로그, 검색·서비스 필터·개인 즐겨찾기 |
| 알림 | 담당 작업과 검토 요청을 프로젝트별로 확인하고 상세 열기 |
| 프로젝트 설정 | 참여자, 파트와 관리 권한, 프로젝트 관리 |
| 개인 설정 | 이름, 디자인·포인트 컬러·라이트/다크 모드, 한국어·영어, 앱 버전과 업데이트 |

작업·일정·연결은 프로젝트 사이드바에서 이동합니다. 제목줄의 뒤로·앞으로 이동은 전역 탐색이며 프로젝트 사이드바의 열림 상태는 유지됩니다. 설정의 항목 목록과 메인 상세 화면은 별도 영역입니다. 좁은 창에서는 가로 스크롤·줄바꿈·접힘을 사용합니다.

신규 프로젝트는 **작업과 파트가 비어 있는 상태**로 시작합니다. 칸반은 **확인중·진행중·검토중·완료·보류·드랍 6열**을 사용합니다. 상태는 작업 전체의 진행 상황이고, 현재 담당자와 검토·수정 목적은 배정 정보입니다. 자동 테스트의 예시 데이터는 제품 실행이나 프로젝트 생성 때 불러오지 않습니다.

## 시작하기

프로젝트 사이드바의 **바로가기**는 **등록된 바로가기**와 **도구 추가** 탭으로
구분합니다. 새 프로젝트의 등록 목록은 비어 있으며, 이전 형식의 `null` 목록도
빈 목록으로 표시합니다. GitHub 저장소 링크를 자동 등록하지 않습니다. 기존에
저장한 링크는 그대로 유지합니다.

**도구 추가**에서는 Google Drive, Notion, Jira, Discord, 카카오톡, GitHub,
Figma, Slack을 추천 카탈로그로 제공합니다. **추가**를 누르고 팀 폴더·보드·채팅방
주소를 입력하거나, 직접 URL을 붙여넣어 바로가기를 등록합니다. 주소에 맞는
서비스를 자동으로 인식하며, 사이트의 실제 favicon을 탐색해 미리보기합니다.
사이트 아이콘을 가져오지 못하면 로컬 서비스 SVG 또는 기본 링크 아이콘을 사용합니다.
이 기능은 브라우저에서 팀 링크를 여는 바로가기 등록이며, 서비스 계정 인증이나
API 데이터 연동을 수행하지 않습니다.

등록 카드 클릭은 링크를 열고, **더보기**에서 수정·복사·삭제합니다. 검색과 서비스
필터로 찾거나 이름 순·등록 순으로 정렬할 수 있습니다. 개인별 즐겨찾기와 표시
설정은 이 기기에 저장되며 팀의 링크 설정과 분리됩니다. 로컬 서비스 아이콘의
출처와 라이선스 고지는 `third_party/simple-icons/`에 있으며 배포본에도
`data/licenses/simple-icons/`로 포함됩니다.
저장한 바로가기는 `.ieum/project.json`에 포함되어 팀원과 동기화됩니다.
승인된 참여자는 추가·수정·삭제할 수 있으며, 동시에 수정된 목록은 덮어쓰지 않습니다.
카탈로그 탐색과 아이콘 미리보기는 팀의 등록 목록이나 작업 데이터·전송 대기열을
생성하지 않습니다. 삭제한 링크와 빈 목록은 다시 생성되지 않습니다. 링크는 HTTPS
주소를 지원하며 기본 브라우저로 엽니다.

구성 참고: [Jira 프로젝트 바로가기](https://support.atlassian.com/jira-software-cloud/docs/add-edit-or-delete-a-shortcut/),
[Notion 북마크](https://www.notion.com/help/embed-and-connect-other-apps),
[Fluent 카드 구성과 동작](https://fluent2.microsoft.design/components/web/react/core/card/usage),
[Slack 앱 탐색과 설치](https://slack.com/help/articles/360001537467-Guide-to-apps-in-Slack).

개인 설정의 **디자인**에서 라이트·다크 모드와 포인트 컬러를 선택합니다.
기본 색상이나 `#RRGGBB` 형식의 사용자 지정 색상을 사용할 수 있습니다.
**언어**에서는 한국어·영어를 선택하며 화면에 바로 반영됩니다. 작업·프로젝트의
사용자 입력 내용은 번역하지 않습니다. 개인 설정은 프로젝트 데이터와 별도의
로컬 파일에 저장되어 프로젝트 전환·로그아웃·앱 재실행 후에도 유지됩니다.

1. Windows 배포본 `Ieum-Windows-x64.exe`를 실행합니다. Git, Flutter SDK와 개발 도구 설치는 필요하지 않습니다. ZIP을 사용하면 전체를 풀고 `ieum_flutter.exe`를 실행합니다.
2. **GitHub로 로그인**을 누르고 브라우저에서 인증 코드를 승인합니다. 로그인 유지 시 운영체제 자격 증명 보관소를 사용합니다.
3. 저장소 관리자는 프로젝트 이름·GitHub 저장소·닉네임으로 **프로젝트 생성**을 진행합니다. 한 저장소에 하나의 이음 프로젝트를 만듭니다. 빈 저장소도 초기화할 수 있습니다.
4. 팀원을 GitHub 저장소 협업자로 초대합니다. 팀원이 초대를 수락하고 같은 저장소에 **프로젝트 참여**를 요청하면 이음의 관리자가 승인합니다.
5. 프로젝트 설정에서 필요한 파트를 만들고 참여자에게 배정합니다. 작업을 등록하고 필요하면 본인 작업으로 잠급니다.

로컬 저장 위치는 자동으로 준비합니다. 다른 폴더가 필요하면 생성·참여 화면의 **저장 위치 변경**에서 지정합니다. 기존 프로젝트의 DB와 선택 경로는 그대로 사용하며 로그아웃해도 지워지지 않습니다.

다른 프로젝트는 프로젝트 선택기에서 생성·참여·전환합니다. 프로젝트마다 작업과 전송 대기열을 분리하며 로그인 유지 시 마지막 프로젝트를 복원합니다. 같은 GitHub 계정은 다른 PC에서도 같은 참여자로 식별합니다.

## 상태·담당자 전달·잠금

칸반은 **확인중·진행중·검토중·완료·보류·드랍**을 사용합니다. 확인중은 담당자가 아직 시작하지 않은 작업이며, 알림 읽음 여부와 별개입니다. **잠금 없는 확인중·진행중·검토중 작업은 모든 활성 참여자가 수정할 수 있습니다.** 현재 담당자와 파트는 내 할 일과 알림을 위한 정보입니다.

진행중 또는 검토중에서 **담당자에게 전달**을 선택하면 받은 작업은 **확인중**으로 이동합니다. 받을 파트·개인, 작성·검토·수정 목적과 코멘트를 확인하고 **최종 확인**합니다. 받은 담당자가 시작하면 작성·수정은 진행중, 검토는 검토중으로 이동합니다. 검토 의견은 코멘트로 남기고 필요하면 수정 목적으로 다시 전달합니다. 별도 반려 동작과 자동화 실행은 사용하지 않습니다.

**보류**와 **드랍**에는 사유가 필요합니다. 보류에서 작업 재개를 선택하면 보류 전 상태로 돌아가며, 드랍에서 작업 복귀를 선택하면 확인중으로 돌아갑니다. 내용·코멘트·담당자·잠금은 유지됩니다. 드랍은 일정에서 제외되며 칸반과 상태 필터에서 관리합니다.

새 작업 등록에서 **잠금 없음 / 작성자만 수정 / 지정 작업자만 수정**을 선택합니다. 기존 작업 상세에서는 **내 작업으로 잠금**을 선택할 수 있습니다. 잠금 담당자만 내용·상태·전달·삭제·보관을 변경할 수 있고, 다른 활성 참여자는 열람·코멘트를 할 수 있습니다. 관리자도 다른 사람의 잠금을 해제할 수 없습니다.

전달 확인창의 **잠근 채 전달**을 선택하면 **특정 담당자 한 명**을 지정해야 합니다. 전달과 잠금 이전은 하나의 작업 변경으로 처리합니다. 이전 담당자는 수정할 수 없고 받은 담당자만 수정할 수 있습니다. 잠금을 해제해 파트 전체로 전달하면 해당 파트에 내 할 일과 알림이 표시되고 모든 활성 참여자가 수정할 수 있습니다. 확인 중 작업 버전이나 참여자 정보가 바뀌면 다시 확인해야 합니다.

작업 목록·칸반 카드의 **핀 버튼**이나 상세의 **상단에 고정**을 선택하면 일반 작업보다 앞에 표시합니다. 고정 작업끼리는 **높음 → 보통 → 낮음** 순서로 정렬하며, 같은 우선순위는 선택한 정렬을 따릅니다. 칸반은 각 상태 열의 상단에 표시합니다. 고정 상태는 저장·동기화되며 잠긴 작업은 잠금 담당자만 고정을 바꿀 수 있습니다.

작업 상세의 작성 기록은 **작성자·작성일**로 표시합니다. 현재 담당자는 전달할 때 변경되며 최초 담당자를 별도 항목으로 반복해서 표시하지 않습니다. 이전 데이터의 최초 담당자 필드는 호환성을 위해 보존합니다. 작성 기록이 없는 기존 작업은 추측하지 않고 기록 없음으로 표시합니다. 전달·검토·상태 이동의 최근 100건을 담당자·시각·코멘트와 함께 작업 상세에 표시하고 GitHub에 동기화합니다. 검토중에 남긴 코멘트는 검토 코멘트로 표시합니다.

코멘트는 작성자·작성 시각과 함께 GitHub에 동기화합니다. 기존 코멘트 수정·삭제를 허용하지 않으며 동시 코멘트는 ID를 기준으로 합칩니다. 작업당 100개, 각 2000자까지 등록할 수 있습니다.

일정 달력과 날짜별 목록은 **작업 지정일~마감일을 양 끝 날짜까지 포함**합니다. 같은 작업은 날짜 칸을 가로지르는 연속 막대로 표시하고 주가 바뀌면 다음 줄에서 이어집니다. 지정일과 마감일 사이의 날짜를 눌러도 해당 작업이 표시됩니다. 마감일이 없으면 지정일만 표시하고 마감 미정 목록에 남습니다. 계산은 현재 달력의 42일과 선택한 월의 타임라인으로 제한합니다.

작업을 보관하면 목록과 일정에서 숨기고 보관함에서 복원합니다. **작업 상세 → 삭제 → 삭제 확인**으로 삭제하면 목록·칸반·일정과 관련 알림에서 제외되며 앱에서 복원할 수 없습니다. 잠긴 작업의 삭제·보관도 잠금 담당자만 가능합니다. 삭제 표식과 제출 이력은 재등장 방지와 동기화 검증을 위해 보존합니다. 잠금·전달·내용 수정·삭제가 다른 사람의 미통합 변경과 충돌하면 양쪽 변경을 보존합니다.

세부 설계와 검증은 [일정과 작업 잠금](docs/task-lock-and-schedule-plan.md)을 참고하세요.

## 작업 자료

작업 상세의 **자료**에서 파일과 HTTPS 링크를 최대 30개까지 첨부합니다. 파일당 기본 한도는 **50MB**이며 프로젝트 관리자가 **프로젝트 설정 → 일반 → 자료**에서 1~50MB로 조절합니다. 변경한 한도는 새 파일에 적용하고 기존 첨부는 유지합니다. 작업의 잠금과 내용 수정 규칙이 자료 추가·제거에도 적용됩니다.

작업 설명은 Markdown으로 표시합니다. `.md`·`.markdown` 파일은 상세 안에서 펼쳐 읽을 수 있으며, 미리보기는 256KB까지 지원합니다. 다른 형식과 더 큰 Markdown 파일은 다운로드합니다. 문서의 외부 이미지도 자동으로 받지 않고 링크로 열 수 있습니다.

파일 내용은 작업 JSON과 분리해 `ieum/attachments` 브랜치의 `.ieum/files/<SHA-256>`에 저장합니다. 같은 파일은 중복 업로드하지 않으며, 파일 업로드가 완료된 뒤 작업 변경을 제출합니다. 자료 제거는 작업에서 연결을 해제하며 GitHub에 남은 파일과 커밋 이력은 지우지 않습니다.

전송 대기 파일은 DB 옆 `<DB 파일명>.resources/pending`에 보존하므로 프로젝트 이동 시 해당 폴더도 함께 옮겨야 합니다. 다운로드 캐시는 같은 폴더의 `cache`에서 최대 200MB로 정리합니다. 작업에 등록되지 못한 임시 첨부는 제거하고, 전송 오류가 난 파일은 재시도를 위해 보존합니다. JSON 수동 내보내기에는 파일 본문이 포함되지 않습니다.

## 파트와 관리 권한

파트는 기획·QA·PD 등 사용자가 만드는 직무 구분입니다. 기본 파트는 없으며 프로젝트 소유자도 파트를 배정받을 수 있습니다. 파트 이름을 추가했다고 자동으로 관리자가 되지는 않습니다.

별도로 지정하는 관리 권한은 참여자 관리와 파트 관리입니다. 프로젝트 소유자는 프로젝트와 워크플로 정의를 관리합니다. 작업 등록·진행·검토 등에 예전의 기능별 역할 권한을 다시 부여할 필요는 없으며, 실제 작업 처리 범위는 활성 참여 여부와 현재 처리 대상·상태·전환 조건으로 결정합니다.

GitHub 저장소 권한과 이음의 작업 규칙은 별개입니다. 저장소 쓰기 권한을 가진 사용자의 GitHub 직접 변경을 앱이 차단하지는 않습니다. 참여 중지나 이음 소유권 이전이 GitHub 저장소 협업자·소유권을 자동으로 변경하지 않습니다.

## 동기화와 복구

작업 저장과 전송 대기열 기록은 하나의 SQLite 트랜잭션에서 처리합니다. 저장한 변경은 작업별 브랜치·PR로 전송되고 현재 참여자·작업 버전·워크플로 규칙을 검증한 뒤 통합합니다. 수신은 통합된 변경을 개인 DB에 적용합니다.

- 로컬 저장과 팀 반영은 서로 다른 상태입니다. 연결 화면의 대기·보류·오류를 확인할 수 있습니다.
- 오프라인이나 자동 동기화가 꺼진 동안에도 로컬 변경을 보존하고 다시 연결하면 전송합니다. 오류와 GitHub 요청 제한에는 재시도 간격을 늘립니다.
- 자동 전송·통합은 앱이 실행 중일 때 동작합니다. 앱이 모두 종료된 동안 실행되는 별도 서버나 예약 작업은 없습니다.
- 같은 작업의 PR을 재사용하고 이미 통합한 변경을 복구합니다. 다른 작업의 충돌은 격리해 처리하며, 보호 브랜치 조건은 우회하지 않습니다.
- 워크플로 상태·처리 대상·처리 목적·전환 ID·완료일·코멘트는 하나의 변경으로 병합합니다. 두 사람의 서로 다른 전환을 임의로 섞지 않습니다.
- 충돌 시 로컬 내용과 기준본을 보존합니다. 개인 변경을 백업하고 통합본을 적용할 수 있으며 백업을 자동 재전송하지 않습니다.
- 저장 순서의 검증용 중간 버전을 전송하여 잠금 이후 편집이나 필수 입력을 우회한 전환을 검사합니다. 팀 전체의 영구 감사 이력 제품을 제공하는 것은 아닙니다.
- 로컬 표시용 활동은 통합된 작업별 최근 100개로 정리합니다. 미통합 변경의 활동·검증 순서·복구 백업은 보존합니다. 알림은 최근 500개를 읽고 읽은 알림은 사용자별 최근 500개를 유지하며, 읽지 않은 알림은 자동 삭제하지 않습니다.
- 읽지 못한 전송 대기열·완료 기록은 원본과 오류를 복구 기록에 보관합니다. 연결 화면과 연결 설정의 **복구 기록**에서 발생 시각·대상 작업·발생 이유·원본 오류를 확인합니다. 경고나 기록 창의 **확인**을 누르면 확인한 경고는 재실행 후에도 숨기며 기록은 유지합니다. 이후 발생한 새 복구 건은 다시 안내합니다.

GitHub에는 프로젝트 설정과 작업 JSON을 보내며 개인 SQLite 파일은 전송하지 않습니다. 작업별 제안은 `.ieum/changes/<GitHub 계정>/<작업 ID>.json`에 저장합니다. 수동 JSON 내보내기·가져오기를 지원하며 누락된 작업을 물리적 삭제로 해석하지 않습니다.

Windows 로그인·GitHub API는 시스템 프록시와 인증서 검증을 사용하는 WinHTTP 통신을 적용합니다. 인증서·DNS·프록시·시간 초과 오류를 구분해 안내합니다. [인증 연결 보완](docs/github-auth-connectivity.md)을 참고하세요.

## 로그인·저장·업데이트

인증은 GitHub OAuth Device Flow를 사용합니다. 공개 Client ID를 포함하지만 Client Secret은 사용하지 않습니다. 저장소 작업을 위해 `repo` 권한을 요청합니다. 로그인 유지 시 Windows 자격 증명 관리자 또는 Linux Secret Service 키링에 인증 정보를 보관합니다. 프로젝트 DB·설정 목록·JSON·배포본에 토큰을 넣지 않습니다. 고급 세션 토큰은 메모리에만 남습니다.

프로젝트 DB 파일은 `ieum-<프로젝트 ID>-gh-<계정 ID>.sqlite`입니다. Windows의 기본 프로젝트 목록은 `%APPDATA%\Ieum-Flutter-Prototype\project-preferences.json`, 신규 DB 기본 폴더는 그 옆의 `projects`입니다. 경로는 기존 사용자 호환을 위해 유지합니다. `IEUM_FLUTTER_DATA_DIR` 환경 변수로 설정 디렉터리를 바꿀 수 있습니다.

Windows EXE 런처는 `%LOCALAPPDATA%\Ieum\builds\<빌드 시각>`에 앱과 런타임을 풉니다. 공개 배포 저장소 `devbin-lab/ieum`의 정식 GitHub Releases에서 업데이트를 확인하며 EXE 크기와 SHA-256을 검사합니다. 시작 시와 4시간마다 확인하고 다음 실행 또는 **업데이트 후 재시작**으로 적용합니다. 시작에 실패한 업데이트는 격리하고 가능한 이전 버전으로 복구합니다. 시작 완료 후 사용 중 종료된 경우에는 새 데이터 형식과의 호환성을 보호하기 위해 이전 버전을 자동 실행하지 않습니다. 종료 코드는 작업 내용이나 인증 정보 없이 `last-launch-error.txt` 한 파일에 기록합니다. `IEUM_DISABLE_UPDATES=1`은 개발 실행의 업데이트를 끕니다.

Linux는 [Linux 안내](linux/README-Linux.md)를 따르며 전체 tar.gz를 교체하는 수동 업데이트 방식입니다. 이 작업에서 Linux 실행 환경 검증을 수행했다고 간주하지 않습니다.

## 개발과 로컬 배포

Flutter 3.47.5 / Dart 3.13.4 기준입니다. Windows 개발 빌드에는 MSVC C++ 도구와 CMake가 필요합니다.

```powershell
flutter pub get
flutter analyze
# 변경 영역의 단위·위젯 테스트를 지정해서 실행합니다.
flutter test test/project_test.dart
.\build-windows.ps1
.\package-windows.ps1
# 별도 검증 빌드를 패키징할 때:
.\package-windows.ps1 -ReleaseDirectory build\windows\v1-release\runner\Release
```

패키징은 `pubspec.yaml`, `lib/app_release.dart`, 실제 EXE의 버전 일치와 필수 엔진·SQLite·폰트·런타임 파일을 검사합니다. 개인 DB·환경 파일·예시 데이터를 거부하고 네이티브 자산의 개발 PC 절대 경로를 제거합니다. 같은 빌드 ID의 산출물을 덮어쓰지 않습니다.

산출물은 저장소 루트 `dist/windows/<빌드 시각>/`의 EXE·ZIP·사용안내·`SHA256SUMS.txt`입니다. 이 스크립트는 GitHub Release 게시나 소스 푸시를 수행하지 않습니다. 공개 배포 시 `v1.0.0` 태그와 정식 릴리즈의 `Ieum-Windows-x64.exe` 자산이 업데이트 소스가 됩니다. 이전 배포 내역과 파일은 [Beta 통합 릴리즈](https://github.com/devbin-lab/ieum/releases/tag/beta)에 보관합니다.

## 검증 경계

개발 검증은 정적 분석, 변경에 필요한 단위·위젯·가짜 GitHub API 검사, Release 빌드와 프로세스 시작 확인으로 제한합니다. 테스트는 임시·메모리 DB를 사용하며 실제 프로젝트에 샘플 작업이나 PR을 만들지 않습니다.

팀 환경에서의 OAuth 승인, 두 PC 간 실제 전송·통합, 보호 브랜치 설정, 실제 사용자 워크플로, 최종 화면 조작과 업데이트 수용 검증은 별도로 진행해야 합니다. 실행 파일 생성과 프로세스 생존 확인을 모든 실제 업무 동작의 검증으로 표현하지 않습니다.

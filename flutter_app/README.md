# 이음 · Flutter 데스크톱

Flutter 3.47.5 / Dart 3.13.4로 만든 Windows 프로토타입입니다. GitHub 인증과 프로젝트별 개인 SQLite를 사용하며 새 프로젝트는 빈 작업 목록으로 시작합니다. 개발 브랜치는 `codex/flutter-desktop`입니다. 이전 Electron 예시 구현도 보존되어 있으며 Electron 기준 브랜치는 `codex/electron-prototype`입니다.

## 실행

저장소 루트의 `Start-Ieum-Flutter.bat`을 실행하거나 `build/windows/x64/runner/Release/ieum_flutter.exe`를 실행하세요. Release 폴더 전체가 실행 패키지입니다. exe 옆의 DLL과 data 폴더를 함께 유지해야 합니다. 빌드된 앱을 실행하는 팀원 PC에는 Flutter SDK나 Node.js가 필요하지 않습니다. Windows의 Microsoft Visual C++ 런타임은 필요합니다.

현재 PC에는 Release 빌드가 준비되어 있습니다. 개발용 빌드 폴더는 Git에 포함되지 않습니다. 소스만 복제한 경우 아래 절차로 빌드하세요.

```powershell
flutter pub get
flutter analyze
flutter test
flutter build windows --release
```

현재 PC처럼 Visual Studio의 게임용 C++ 도구가 설치되어 있고 CMake가 별도로 있는 경우, `build-windows.ps1`은 일반 Flutter 빌드를 먼저 시도한 뒤 기존 MSVC와 CMake로 표준 Windows runner를 빌드합니다. Flutter SDK나 Visual Studio 설치 구성을 변경하지 않습니다. SDK가 PATH에 없으면 `%USERPROFILE%\develop\flutter`를 확인합니다.

## 동작

- 앱 색상에 맞춘 커스텀 타이틀바. 제목·빈 공간을 드래그해 창 이동, 더블클릭으로 최대화·복원, 오른쪽 버튼으로 최소화·최대화·닫기. 창 가장자리의 크기 조절은 Windows에 맡깁니다.
- 모든 앱 내 드롭다운은 둥근 팝오버·선택 체크·호버 강조를 사용하는 공통 UI입니다. 날짜 선택 달력, 알림·재작업·통합 충돌 창과 툴팁도 같은 스타일을 사용합니다. 파일 열기·저장은 Windows 기본 대화상자를 사용합니다.
- 통합된 ‘일정 · 작업’ 화면에서 목록·칸반보드 보기를 선택합니다. 검색·파트·내 할 일 필터는 보기 전환 시 유지되며 같은 작업 데이터를 표시합니다.
- 칸반 5단계와 드래그 이동: 할 일 / 진행 중 / 검토 / 재작업 / 완료.
- 작업 등록·수정, 파트별 기본 담당자·검토자 배정, 우선순위 높음·보통·낮음.
- 일정표: 작업내용, 상태, 원 작업자, 현재 처리자, 지정일, 마감일, 완료일.
- 검색·파트 필터·내 할 일·내 검토 요청.
- 검토 요청 시 현재 처리자를 검토자로 전환; 재작업은 사유 입력 후 원 작업자로 전환; 완료 승인 시 완료일 기록.
- SQLite 저장, 활동 기록, Discord 알림 이벤트 미리보기.
- 공통 JSON 변경안 내보내기, 통합본 가져오기, 3-way 병합·충돌 감지.

실행 시 GitHub 로그인과 프로젝트 시작 화면을 표시합니다. 새 프로젝트는 예시 작업이나 예시 사용자 없이 시작합니다. 예시 작업 파일과 사용자 전환은 자동 테스트에서만 사용합니다. Discord 전송과 후속 제작 파트의 작업 자동 생성은 연결 전입니다. Discord 이벤트는 SQLite outbox에 미리보기 상태로 보관합니다.

## 로그인 · 프로젝트 생성 · 참여

1. 저장된 Git 인증 또는 세션 토큰으로 GitHub 계정을 확인합니다. ‘GitHub 계정 만들기’는 GitHub의 가입 화면을 엽니다. 이음은 비밀번호를 별도로 만들거나 저장하지 않습니다.
2. 개설자는 ‘프로젝트 생성’에서 프로젝트 이름, GitHub 저장소, 닉네임, 개인 DB 저장 폴더를 지정합니다. 이미 main 브랜치가 있는 저장소의 관리자여야 합니다. `.ieum/project.json`에 빈 프로젝트와 최초 개설자 정보를 등록하고, 선택한 폴더에 새 SQLite DB를 만듭니다. 한 저장소에 한 프로젝트만 생성할 수 있으며 기존 프로젝트를 덮어쓰지 않습니다.
3. 개설자는 ‘연결 설정 → 참여자 · 역할과 권한 → GitHub 협업자 초대’에서 팀원의 GitHub 계정을 초대합니다. 팀원이 GitHub에서 초대를 수락해야 합니다.
4. 참여자는 GitHub 로그인 후 ‘프로젝트 참여’에서 같은 저장소, 닉네임, 자신의 DB 폴더를 지정합니다. `ieum/members/<닉네임 식별자>-gh-<계정 ID>` 브랜치와 가입 요청 PR을 만듭니다. 한글 닉네임은 안전한 영문·숫자 식별자로 변환합니다. 계정 ID가 포함되므로 같은 닉네임도 브랜치가 겹치지 않습니다.
5. 개설자는 참여자 관리에서 새로고침 후 가입 요청의 역할과 파트를 지정해 승인합니다. 승인 시 프로젝트 설정을 갱신하고 가입 요청 PR을 닫습니다. 승인 전 참여자는 작업 등록·수정·상태 변경을 할 수 없습니다. 역할 변경은 자동 동기화 때 갱신됩니다.

| 역할 | 앱에서 허용하는 작업 |
| --- | --- |
| 개설자 | 프로젝트 관리, 협업자 초대, 가입 승인, 역할·파트 지정, 작업 등록·배정·통합 승인 |
| PD / PM | 작업 등록·배정·일정·우선순위 변경, 작업 처리, 통합 승인 |
| 작업자 | 배정된 작업의 제목·설명 수정, 진행·검토 요청, 자신에게 배정된 검토 승인·재작업 요청 |
| 열람자 | 작업·일정 조회 |
| 가입 승인 대기 / 참여 중지 | 조회만 가능, 작업 제출 차단 |

닉네임은 표시 이름이며 로그인 신원과 권한은 GitHub의 숫자 계정 ID와 프로젝트 설정으로 구분합니다. 사용자 전환 메뉴는 실제 프로젝트에서 제공하지 않습니다. 전송·통합·역할 변경 전에는 원격 프로젝트 설정과 인증한 계정을 다시 확인합니다.

**권한 범위:** 이음 역할은 앱 동작을 제한합니다. GitHub 저장소의 협업자 권한과는 별개입니다. 현재 서버 없는 구조에서는 저장소 쓰기 권한을 받은 사용자가 GitHub나 다른 클라이언트를 직접 사용하면 main과 프로젝트 설정을 수정할 수 있습니다. 악의적 변경까지 저장소 차원에서 차단하는 보호 브랜치·필수 검사·서버 검증은 아직 구성하지 않았습니다. 참여 중지로 GitHub 협업자 권한을 자동 회수하지도 않습니다. 민감한 실제 팀 운영 전에는 저장소 접근 정책을 별도로 구성해야 합니다.

## GitHub 자동 동기화

프로젝트 생성·참여 후 해당 저장소에 자동 동기화를 켭니다. 실제 프로젝트의 저장소는 연결 화면에서 임의로 바꾸지 않으며 로그아웃 후 다른 프로젝트에 참여합니다. 테스트용 기본 입력은 `devbin-lab/ieum-test-fresh`입니다. 대상 저장소에는 main 브랜치가 있어야 하며, 현재 구현은 같은 저장소에 쓰기 권한을 가진 팀원이 사용하는 방식입니다. 별도 fork를 통한 제출은 지원하지 않습니다.

- 작업 등록·수정·상태 변경을 개인 DB에 저장하면서 전송 대기열도 함께 저장합니다. 저장 뒤 자동으로 작업별 브랜치에 JSON을 커밋하고 PR을 만듭니다. 같은 작업의 열린 PR에는 변경을 추가하고, 다른 작업은 새 PR로 제출합니다. 이미 통합된 작업을 다시 수정하면 새 PR을 만듭니다.
- 작업 브랜치는 개인 참여 브랜치 아래의 `<개인 브랜치>/<작업 ID>`, 파일은 `.ieum/changes/<GitHub 계정>/<작업 ID>.json`입니다. 앱 소스나 SQLite 파일은 제출하지 않습니다. 로컬 Git checkout을 바꾸지 않고 GitHub API로 커밋과 PR을 생성합니다.
- 전송 실패 시 개인 작업과 대기열을 보존하고 30초마다 재시도합니다. 응답 유실 후 재시도해도 같은 내용의 커밋과 열린 PR을 재사용합니다. 실행 중 새 수정이 생겨도 이전 전송 응답이 새 대기열을 덮어쓰지 않습니다.
- 앱 실행 중 30초마다 통합 브랜치를 확인하고 승인된 작업을 개인 DB에 가져옵니다. ‘지금 동기화 / 재시도’로 즉시 확인할 수도 있습니다. 같은 필드의 다른 변경은 전체 가져오기를 멈추고 연결 화면에 두 값을 표시합니다. 작업에서 값을 맞춘 뒤 다시 동기화하세요.
- 개설자와 PD / PM은 연결 화면의 ‘팀의 통합 승인 대기 → 변경 확인’에서 실제 PR 변경 내용을 보고 ‘통합 승인’을 누를 수 있습니다. 검토했던 커밋이 바뀌면 승인을 거부하고 재검토하도록 합니다. 승인 직후 통합본을 가져옵니다. 승인 자체는 자동으로 처리하지 않습니다.

인증은 컴퓨터에 이미 저장된 Git 인증을 사용하거나 로그인 창에 세션 토큰을 입력합니다. Git 인증 조회는 브라우저나 로그인 창을 자동으로 열지 않습니다. 토큰 사용 시 대상 저장소의 Contents 및 Pull requests 읽기·쓰기 권한이 필요합니다. 협업자 초대에는 저장소 관리 권한도 필요합니다. 토큰은 앱 메모리에만 보관하고 DB·JSON에 저장하지 않습니다. 저장된 Git 인증이 없다면 앱 재실행 후 토큰을 다시 입력해야 합니다.

GitHub 계정 권한과 저장소 규칙이 실제 전송·통합 가능 여부를 결정합니다. 보호된 브랜치가 추가 검토나 검사 통과를 요구하면 해당 조건을 충족해야 합니다.

프로젝트마다 고유 ID와 빈 기준본으로 시작하며, 승인된 작업과 참여자 설정을 공유합니다. 자동 가져오기는 최대 1,000개 관리 파일, 파일당 1MB까지 지원하며 GitHub 사용량 제한이나 네트워크 상태에 따라 지연될 수 있습니다.

| lib/project_service.dart | GitHub 로그인, 프로젝트 설정, 개인 브랜치·가입 PR, 초대·역할 지정 |
| lib/project_gate.dart | 로그인, 프로젝트 생성·참여, DB 저장 폴더 선택, 최근 프로젝트 열기 |
| lib/team_panel.dart | 참여자 목록, 역할·파트 지정, 가입 승인 |

DB는 생성·참여할 때 선택한 폴더의 `ieum-<프로젝트 ID>-gh-<계정 ID>.sqlite`에 보관합니다. `%APPDATA%\Ieum-Flutter-Prototype\project-preferences.json`에는 최근 프로젝트 경로와 저장소 정보만 기록합니다. 로그아웃해도 작업 DB는 보존하며 재로그인 후 ‘최근 프로젝트 열기’를 사용합니다. 이전 `ieum.sqlite` 예시 DB는 현재 앱에서 자동으로 열지 않습니다. `IEUM_FLUTTER_DATA_DIR`는 설정 파일 위치를 바꿉니다. DB 파일은 커밋하지 않습니다.

작업 JSON은 `schemaVersion: 1`을 사용하며 변경안은 `projectId/baseRevision/authorId/changes`, 통합본은 `projectId/revision/tasks`를 포함합니다. 실제 프로젝트의 projectId는 생성 시 UUID로 지정합니다. 동일 항목 충돌과 날짜·상태 관계가 맞지 않는 통합은 전체 반영을 멈춥니다. 삭제 병합은 현재 지원하지 않습니다. 예시 테스트 통합본은 `assets/demo-snapshot.json`이며 기존 Electron 예시 계정은 새 프로젝트의 GitHub 계정·역할과 호환하지 않습니다.

## 앱 자동 업데이트와 릴리스

현재 앱 버전은 `0.1.1+2`입니다. 업데이트는 작업 데이터 저장소와 별도로 `devbin-lab/ieum`의 GitHub Releases를 사용합니다. 시작 시와 4시간마다 최신 정식 릴리스를 확인하며, GitHub가 제공하는 EXE 크기와 SHA-256 digest를 검증한 뒤 `%LOCALAPPDATA%/Ieum/updates/<버전>`에 보관합니다. 실패하거나 파일이 변조되면 기존 앱과 DB를 유지합니다. 검증된 업데이트는 다음 실행 시 자동 적용하고, 제목줄의 ‘업데이트 후 재시작’으로 바로 적용할 수도 있습니다. 재시작 도우미는 기존 앱 프로세스 종료를 기다린 뒤 새 앱을 엽니다. 프로젝트 DB·로그인 설정은 앱 배포 폴더와 분리되어 보존됩니다.

현재 배포 저장소는 비공개이므로 이용자는 `devbin-lab/ieum`에 읽기 권한이 있어야 하며 GitHub 로그인 후 업데이트를 확인합니다. 세션 토큰을 사용할 때에는 배포 저장소 읽기 권한도 포함해야 합니다. 업데이트에서 인증 토큰은 `api.github.com`에만 전달하고 다운로드 주소 이동 시에는 전달하지 않습니다. `IEUM_DISABLE_UPDATES=1`로 실행하면 자동 확인과 실행 전 업데이트 적용을 끌 수 있습니다.

개발자는 `pubspec.yaml`과 `lib/app_release.dart`의 버전을 함께 올리고 Release 빌드 후 `package-windows.ps1`로 배포본을 만듭니다. 해당 소스 커밋에 `v<버전>` 태그(예: `v0.1.1+2`)를 붙이고, GitHub Releases에 정확히 `Ieum-Windows-x64.exe` 이름으로 첨부하여 정식 릴리스를 게시합니다. Draft·Pre-release는 자동 업데이트 대상에서 제외합니다. ZIP은 수동 설치용입니다. 기존 `0.1.0+1` EXE에는 업데이트 기능이 없으므로 최초 한 번은 새 EXE로 교체해야 합니다. OAuth 로그인은 별도 구현 전이며 현재 버전은 저장된 Git 인증 또는 세션 토큰을 사용합니다.

## 검증 결과

다른 PC용 단일 EXE는 Windows Release 빌드 후 `package-windows.ps1`로 만듭니다. `dist/windows/<빌드 시각>/Ieum-Windows-x64.exe`에 앱, DLL, Visual C++ 런타임과 Flutter 실행 데이터를 포함합니다. 첫 실행 시 `%LOCALAPPDATA%/Ieum/builds/<빌드 시각>`에 풀고 앱을 실행합니다. Flutter SDK가 필요하지 않으며 Windows x64용입니다. 기존 DB, 프로젝트 설정, 인증정보와 테스트 예시는 포함하지 않습니다. ZIP을 사용할 경우 전체 압축을 푼 뒤 실행해야 합니다. 새 테스트 저장소는 `devbin-lab/ieum-test-fresh`입니다. 참여자는 GitHub 협업자 초대와 각자의 GitHub 로그인이 필요하며, 같은 GitHub 계정은 여러 PC에서도 같은 참여자로 처리합니다.

정적 분석, SQLite 저장·재열기, 역할/전환 규칙, 입력 검증, 버전 충돌, JSON 병합, 칸반 드래그, 작업 등록·자동 배정·검토·재작업·승인을 자동 테스트합니다. 1480×940과 1160×740 화면 크기도 화면 조작 없이 테스트 엔진에서 확인합니다.

GitHub 흐름은 가짜 API로 작업별 PR, 중복 재시도, 실패 복구, 전송 중 수정, 승인 후 자동 가져오기, 변경된 커밋의 승인 거부, 충돌 시 DB 보존과 대기열 재열기를 검증합니다. 로그인 신원·빈 프로젝트 DB·가입 PR·역할 제한·원격 권한 회수도 확인합니다. 1160×740 화면에서 로그인·프로젝트 생성·참여자 화면·로그아웃을 화면 제어 없이 검증합니다. 비공개 테스트 저장소 생성은 실제 GitHub에서 확인했지만, 앱으로 실제 가입·작업 PR을 전송·통합하는 실서비스 검증은 아직 하지 않았습니다.

커스텀 타이틀바의 드래그·더블클릭·버튼이 올바른 네이티브 호출로 연결되고, 최대화 상태와 아이콘이 갱신되는지도 테스트합니다. 사용자 요청에 따라 실제 데스크톱 화면 조작 테스트는 진행하지 않았습니다. Windows 파일 선택 대화상자, 실제 창 드래그와 그래픽 드라이버의 실행 동작은 대화형 검증 전입니다.

Release 폴더는 첫 빌드 기준 약 29MB입니다. 이전 Electron 런타임 폴더는 약 367MB였습니다. 두 수치는 압축 전 파일 크기이며 Flutter 개발 SDK·빌드 캐시를 제외합니다. 실행 중 메모리나 CPU 절약률은 Flutter 앱을 실제 실행하여 같은 조건에서 측정하기 전까지 확정하지 않습니다.

현재 DB 처리는 작은 프로토타입 데이터에 맞춰 동기적으로 구현했습니다. 작업 수가 커지면 DB 접근과 JSON 병합을 별도 isolate에서 처리하도록 확장할 계획입니다.

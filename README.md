# 이음 · IEUM

최신 Windows 배포본은 [1.0.0 릴리즈](https://github.com/devbin-lab/ieum/releases/tag/v1.0.0)에서 받을 수 있습니다. 이전 릴리즈의 변경 내역과 배포 파일은 [Beta 통합 릴리즈](https://github.com/devbin-lab/ieum/releases/tag/beta)에 보관합니다. 현재 개발 대상은 Flutter Windows 앱입니다. GitHub 로그인, 빈 프로젝트 생성·참여, 가입 승인과 파트 배정, 작업 목록·칸반·일정·타임라인, 담당자 전달·잠금, 자료 첨부와 GitHub 동기화를 제공합니다. 디자인·언어 설정과 팀 바로가기도 지원합니다. 실행은 `Start-Ieum-Flutter.bat`, 사용 안내는 [flutter_app](flutter_app/README.md)을 참고하세요.

Electron 기준본은 `codex/electron-prototype`, Flutter 작업은 `codex/flutter-desktop`에 분리했습니다. 아래 내용은 기존 Electron 예시 버전에 대한 안내입니다.

팀의 작업과 일정을 연결하는 Electron 데스크톱 프로토타입입니다.
React + TypeScript로 화면을 구성하고 Electron 메인 프로세스에서 개인 SQLite를 관리합니다. 공유 서버 없이 각자 수정한 데이터를 JSON 변경안으로 내보내고, 승인된 통합본을 다시 가져오는 구조입니다.

## 실행

Node.js 24 이상이 설치된 Windows에서 `Start-Ieum.bat`을 실행하세요. 첫 실행에는 의존성과 Electron 런타임을 내려받습니다. 현재 버전은 개발용 실행이며 설치형 exe 배포본은 아직 만들지 않았습니다.

```powershell
npm ci
npm start
```

## 지금 사용할 수 있는 기능

- 할 일 → 진행 중 → 검토 → 완료, 또는 검토 → 재작업 → 진행 중.
- 칸반 카드 클릭과 드래그 이동. 재작업은 사유를 입력한 뒤 요청합니다.
- 작업 등록·수정, 파트별 기본 담당자/검토자 배정, 우선순위 높음/보통/낮음.
- 일정표: 작업내용, 담당자, 현재 처리자, 작업 지정일, 마감일, 완료일.
- 검색, 파트 필터, 내 할 일, 내 검토 요청.
- SQLite 자동 저장, 활동 기록, Discord 알림 이벤트 미리보기.
- 개인 변경안 JSON 내보내기, 통합본 JSON 가져오기, 항목별 3-way 병합과 충돌 감지.

첫 실행에는 예시 작업 8개가 들어 있습니다. 왼쪽 아래 **테스트 사용자**를 바꿔 작업자와 관리자을 체험할 수 있습니다. 실제 로그인·권한 인증 기능은 아닙니다. 검토 상태에서는 원래 작업자를 보존하면서 현재 처리자를 검토자로 표시합니다. 완료 승인 시 완료일을 자동 기록합니다.

## 데이터와 GitHub

개인 DB의 기본 위치는 `%APPDATA%\Ieum-Prototype\ieum.sqlite`입니다. 테스트 환경은 `IEUM_DATA_DIR`로 별도 지정할 수 있습니다. DB 파일과 빌드 산출물은 Git 추적에서 제외됩니다.

GitHub 인증, 자동 커밋·브랜치 생성·PR·main 가져오기는 아직 연결되지 않았습니다. 현재는 `내 변경내역`에서 파일로 내보내거나 가져옵니다. 내보낸 변경안과 가져오는 통합본은 서로 다른 형식입니다. 통합본 형식은 [구조 설계](docs/architecture.md)를 참고하세요.

Discord 토큰은 저장하지 않으며 외부 메시지도 보내지 않습니다. 실제 전송은 승인된 main 반영 이벤트를 기준으로 중복 없이 실행하는 방향입니다. 후속 파트의 새 작업 자동 생성은 배정 규칙만 설계되어 있고 현재 기능에는 포함되지 않습니다.

### 0.4.0: 이름과 역할 관리

- 설정 → 일반에서 표시 이름을 변경하면 현재 컴퓨터의 계정별 프로젝트 목록에 있는 모든 참여 저장소의 `.ieum/project.json`에 커밋합니다. GitHub ID, 참여자 ID, 작업 담당자 ID와 개인 브랜치는 유지됩니다.
- 전송 실패는 프로젝트별로 표시하고 디스크에 재시도 대상을 보관합니다. 실패한 프로젝트를 다시 열 때 재전송합니다. 다른 PC에서만 연결한 프로젝트는 해당 PC에 연결 후 반영해야 합니다.
- 설정 → 역할 · 권한에서 사용자 지정 역할을 만들고 설정 → 참여자 관리에서 배정합니다. 이름 대신 고정 역할 ID로 연결합니다.
- 시스템 권한은 개설자, 관리자, 작업자, 열람자이며 수정할 수 없습니다. 개설자가 역할 관리 권한을 위임할 수 있습니다. 위임받은 사람은 본인이 보유한 권한 안에서만 부여·변경·삭제할 수 있습니다.
- 작업 등록, 배정, 본인 작업, 전체 작업, 지정된 검토, 전체 검토, 다른 작성자의 PR 통합, 참여자 관리, 역할 관리를 분리했습니다. 로컬 편집, 전송, 자동 PR 통합은 최신 원격 역할로 권한을 검증합니다.
- 권한 축소 시 미완료 작업 또는 작성자의 열린 작업 PR이 있으면 인수인계 후 처리합니다. 사용 중인 사용자 지정 역할은 삭제할 수 없습니다. 검토 중인 본문과 완료 작업의 잠금은 관리자에게도 적용됩니다.
- 업데이트 확인·다운로드·재시작 버튼은 설정 → 일반 → 앱 정보로 이동했습니다. 자동 확인과 다운로드는 기존대로 동작합니다.
- 사용자 지정 역할은 0.4.0 클라이언트가 필요합니다. 팀원 전원이 업데이트한 후 사용하세요. 사용자 지정 역할이 없는 이전 프로젝트 설정은 계속 읽을 수 있습니다.

### 0.5.0: 참여자 역할 목록과 활성 상태

- 참여자 편집의 작업자 드롭다운과 담당 파트 칩을 세로 역할 목록으로 교체했습니다. 편집창 안에서 역할을 추가할 수 있으며 기존 파트 데이터는 보존합니다.
- 활성화·비활성화 상태는 역할과 별개로 저장합니다. 비활성화해도 이름, 역할, 담당 파트가 유지됩니다.
- 개설자와 관리자 또는 `member.status` 권한을 부여받은 관리자만 상태를 변경합니다. 개설자는 비활성화할 수 없으며 역할 관리자의 상태 변경에는 역할 관리 권한도 필요합니다.
- 비활성화된 참여자의 작업 수정·진행·업로드와 기존 PR 통합을 차단합니다. 전송 및 통합 시 GitHub의 최신 참여자 상태를 확인하므로 오래된 클라이언트 상태로 업로드할 수 없습니다.
- 상태 변경은 진행 중인 작업이 있어도 즉시 적용합니다. 필요한 인수인계는 관리자가 작업 담당자를 재배정해서 진행합니다. 재활성화하면 다음 동기화에서 대기 작업을 재전송할 수 있습니다.
- 이전 클라이언트에도 비활성 상태가 적용되도록 저장소에는 비활성 역할과 원래 역할을 함께 기록합니다. 사용자 지정 역할에 새로운 상태 관리 권한을 사용할 때에는 팀원 모두 0.5.0 이상으로 업데이트하세요.


### 0.6.0: 역할 관리 UI 검토 및 개선

참여자 탭은 **참여자 관리**로 변경했습니다. 기존 `manager` 권한 묶음은 **관리자**로 표시하며 권한과 기존 참여자 배정은 유지합니다. PD·PM 같은 직무 역할은 자동 생성하지 않습니다. 역할 추가에서 원하는 이름과 권한을 직접 설정합니다.

이번 비교는 공식 도움말에 설명된 화면 구성과 관리 흐름을 기준으로 합니다. 모든 제품의 로그인된 관리자 화면을 직접 실행한 비교는 아닙니다.

기존 화면의 가장 큰 문제는 장식보다 정보 구조였습니다. 역할을 비교하려면 긴 권한 문장을 읽어야 했고, 몇 명이 사용하는지와 왜 삭제할 수 없는지가 보이지 않았습니다. 개선 화면은 검색 가능한 세로 목록, 역할 상세, 권한 분류, 참여자 현황과 삭제 후 재배정 흐름으로 구성합니다. 좁은 창에서는 목록과 상세를 위아래로 배치합니다.

사용자 지정 역할은 미배정 상태에서 바로 삭제할 수 있습니다. 배정된 역할은 참여자 관리 권한으로 다른 역할을 지정해 함께 삭제합니다. 권한이 줄어드는 경우 진행 중인 작업과 대기 PR을 먼저 인수인계해야 합니다. 시스템 권한은 기존 프로젝트의 호환성과 개설자 접근을 위해 고정하며 삭제 대상이 아닙니다.


### 0.6.1: 개설자와 관리자 통일

프로젝트를 만든 사람은 전체 관리 권한을 가진 **관리자**입니다. 기존 개설자의 권한과 저장소에서 사용하는 고정 ID는 유지하고 UI 이름을 통일했습니다. 이전의 별도 관리 권한 묶음은 **운영자**로 표시하여 구분합니다. 운영자가 없는 프로젝트에서는 이 고정 권한을 역할 목록이나 배정 선택에 추가로 표시하지 않습니다. 직접 만든 직무 역할과 기존 참여자의 권한은 그대로 유지합니다.
